# 27. Дослідне зіставлення районів із часовим контекстом

## Джерело й обмеження

Знайдено [відкритий набір карти](https://github.com/zheniaslius/kyiv-air-map/blob/5b82d4c46c828f65b4f945098f8e6801b57ce1b0/public/data/raions.geojson), у якому є десять контурів, позначених як райони Києва. Автор проєкту описує дані як спрощені на основі OpenStreetMap. Використано зафіксований коміт `5b82d4c46c828f65b4f945098f8e6801b57ce1b0` від 13.09.2026 та SHA-256 `4c79a55cbc0ad5f521e49388cd7f606ddeb8222d3b48b25ead4c40845802b8a3`. Дата коміту не підтверджує дату актуальності вихідних меж. Позначення районів і їхні коди взято з файлу; незалежного підтвердження відповідності КАТОТТГ та офіційним межам немає.

© [учасники OpenStreetMap](https://www.openstreetmap.org/copyright), дані OSM поширюються за ODbL. У вихідному репозиторії не знайдено окремого файла ліцензії; умови використання й поширення саме цієї обробленої копії та подробиці перетворень потрібно уточнити. Тому файл використовується лише як **неофіційний дослідний кандидат**: він зберігається локально в `data/raw/geography/` і не включається до Git. Синтетичні результати не є твердженням про офіційні чи актуальні межі.

Усі десять полігонів у перевіреній копії мають валідну геометрію в PostGIS, SRID 4326; площинних перетинів їхніх внутрішніх частин не виявлено. Це технічна перевірка, що не встановлює точності, повноти покриття чи правового статусу. Файл GeoJSON не задає окремої CRS, тому координати трактуються як довгота, широта за стандартом GeoJSON і завантажуються у 4326.

## Що зроблено

В окремій базі `spatial_research` створено дослідні таблиці `candidate_districts`, `temporal_context_snapshot`, `district_context_metadata` і представлення `delivery_district_context`. Як точки використано попередні 500 синтетичних позицій, згенеровані **всередині історичного полігона 2006 року** з документа 26. Позиції не є реальними адресами й не є репрезентативною вибіркою доставок.

До кожної точки приєднано знімок контексту з основної бази для синтетичного сценарію `density_uniform_s42_v1`: експозицію до тривог протягом доставки, погодне значення на її початок і стан тривоги та синтетичного відключення на початок. Час і ID доставки між базами перевіряються перед завантаженням. Погодні опади — за годину **перед міткою** погодного запису, як описано в [документі 25](25_delivery_weather_context.md).

Для геометричного зіставлення використовується `ST_Covers`. Результат має один із трьох станів:

- `matched` — рівно один полігон; зазначено його код і назву з файлу.
- `unmatched` — жодного полігона; доставка й часовий контекст збережені, район `NULL`.
- `ambiguous` — більше одного полігона, зокрема на спільній межі; район не обирається довільно.

Із 500 модельних точок **255 отримали один збіг, 245 не отримали збігу, неоднозначних у цьому наборі немає**. Причина розбіжностей не встановлена: точки походять зі старого полігона, а районні контури — з іншого, спрощеного джерела. Не можна інтерпретувати ці числа як частку реальних доставок за межами міста або як доказ помилки конкретного джерела.

## Перевірка та актуальність

Перед створенням знімка перевірено погодну вітрину та всі дев'ять сценаріїв відключень незалежними еталонами; часові дані зчитано з основної бази одним запитом. Контрольні суми фактів і визначень до та після перевірки збіглися. Усі 500 отриманих просторових результатів зіставлено з незалежним Python-правилом, а всі поля часового знімка — з наявними результатами основної бази. Десять геометрій у PostGIS відповідають зафіксованому файлу.

Окрема SQL-транзакція з відкатом перевірила точку всередині району, на спільній межі двох полігонів і поза ними, а також збереження доставки за відсутності часового контексту. Повторне завантаження наявні об'єкти не перезаписує. Початкову перевірку збережено в `reports/district_context_validation_20261110.json`, повторну з часом перевірки — у `reports/district_context_validation_20261110_rechecked.json`.

**Первинний часовий контекст — статичний знімок, а не живий зв'язок між базами.** Це початкове представлення збережено без змін; воно не перемикається на нові версії. Поле `temporal_context_present` означає наявність запису, а не актуальність. Версійне оновлення та перевірку нового представлення описано в [документі 28](28_versioned_context_refresh.md). Навіть у новому варіанті актуальність перевіряється окремою командою, а не автоматично при SQL-запиті.

## Відтворення та pgAdmin

Потрібні обидві бази, початкові джерела та вже створений просторовий дослід за документом 26, а також наявний сценарій `density_uniform_s42_v1`. Для початкового створення:

```powershell
python -m scripts.district_candidate
python -m scripts.load_district_context
python -m scripts.verify_district_context
```

Перша команда завантажує конкретний файл і перевіряє його SHA-256; якщо файл уже є, вона його не перезаписує. Друга команда створює дослідні об'єкти один раз і також не перезаписує наявні. Якщо вони вже створені, для перевірки достатньо останньої команди. Розповсюджувати оброблений геофайл до з'ясування його умов використання не слід.

У pgAdmin підключіться до `spatial_research` на `127.0.0.1:55433` і відкрийте Query Tool:

```sql
SELECT delivery_id, district_match_status, district_name,
       alert_overlap_seconds, temperature_c, precipitation_previous_hour_mm,
       alert_active, outage_active, scenario_id, temporal_snapshot_utc
FROM spatial_research.delivery_district_context
ORDER BY delivery_id
LIMIT 20;
```

```sql
SELECT district_match_status, count(*) AS deliveries
FROM spatial_research.delivery_district_context
GROUP BY district_match_status
ORDER BY district_match_status;
```

Цей крок підтверджує технічну можливість просторово-часового зіставлення на модельних даних. Для надійного районного дослідження далі потрібні перевірені актуальні межі та правило їхнього оновлення. Версійне оновлення часового знімка реалізовано в документі 28.
