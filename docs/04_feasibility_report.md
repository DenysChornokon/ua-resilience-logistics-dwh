# 04. Звіт про готовність першого етапу (Feasibility Report)

**Проєкт:** UA-Resilience Logistics DWH  
**Дата перевірки:** 28.10.2026  
**Версія:** v0.3 (дані й benchmark перераховано з припущенням `Europe/Kyiv`)  
**Рішення:** **технічний PoC підтверджено; формальне завершення першого етапу ще не підтверджено** через непідтверджену часову зону первинних тривог і відсутню інструкцію відтворення на чистому середовищі.

## 1. Мета та межі дослідження

Перевірити можливість об'єднання історичних повітряних тривог у Києві з погодинними погодними спостереженнями й відтворюваними синтетичними доставками. Реалізувати правильне обчислення тривалості часових перетинів, перевірити коректність алгоритмів і зафіксувати базову продуктивність.

- **Територія:** місто Київ; КАТОТТГ `UA80000000000093317`.
- **Часове вікно:** `[2026-07-01T00:00:00Z, 2026-10-01T00:00:00Z)`; 92 дні.
- **Входить до PoC:** реальні історичні інтервали тривог, погодинні дані, 500 синтетичних доставок, pairwise interval overlap, об'єднання інтервалів, два Python-алгоритми, тести, baseline.
- **Не входить:** причинний аналіз реальних логістичних затримок, повноцінний районний просторовий join, історія блекаутів, production DWH.

Ці події не входять до обраного UTC-вікна PoC.

## 4. Реалізована логіка Interval Join

Для напіввідкритих інтервалів доставки `D=[d_s,d_e)` і тривоги `A=[a_s,a_e)` часовий збіг існує за умов `d_s < a_e` та `a_s < d_e`. Тривалість окремого перетину:

`overlap_seconds = max(0, min(d_e, a_e) − max(d_s, a_s))`.

- `src/poc_interval_join.py` реалізує функцію **попарного** обчислення `overlap_seconds`.
- `scripts/interval_join_baseline.py` реалізує `merge` для об'єднання тривог, `scan` для послідовного перегляду і `indexed` для двійкового пошуку початкового кандидата серед відсортованих інтервалів. Обидва алгоритми повертають по одному числу експозиції на доставку, включно з нулем для неперетинних доставок.
- Додаткова цільова таблиця «один рядок на доставку» з `delivery_id`, `alert_overlap_seconds`, `alert_exposure_ratio`, `overlap_alert_count` **поки не записується в окремий CSV**: це описаний контракт наступної реалізації, а не вже створений файл.
- Поточний join тестує **час і один територіальний ключ**, а не порівняння просторових геометрій.

## 5. Функціональна перевірка і тести

**Pytest:** **10 passed**. Чотири тести перевіряють частковий перетин, відсутність перетину, дотик меж і вкладення; шість перевіряють локалізацію літнього та зимового часу, відхилення неоднозначних і неіснуючих дат, профіль і обробку межі UTC-вікна.

**Додаткові перевірки в baseline:** шість ручних контрольних прикладів пар, чотири доставки зі штучними накладеними тривогами та об'єднанням інтервалів. Для 500 синтетичних доставок проведено 500 × 371 = **185 500 попарних перевірок** базових інваріантів. Результати `scan` і `indexed` однакові. Отримано **154 доставки з ненульовою експозицією (30,8 %)** і **346 без перетину (69,2 %)**; **146** доставок перетинають одну вихідну тривогу, **8** — дві. Сумарний розрахований час експозиції за 500 доставками становить **293 671 секунду**, за прийнятого користувачем припущення `Europe/Kyiv`.

**Обмеження тестів:** наведений `pytest` не охоплює всі некоректні інтервали з `end <= start`, міжрегіональні зіставлення, перетини кількох тривог і матеріалізацію цільової таблиці. Частина цих випадків є додатковими `assert` усередині baseline, але не окремими pytest-тестами.

## 6. Попередній baseline продуктивності

Джерело чисел: **наданий `interval_join_benchmark.csv`**. Виміряно тільки час операції об'єднання разом зі створенням списку результатів, без читання CSV, генерації даних та попереднього злиття інтервалів. **Один запуск на метод і розмір; пам'ять не вимірювалася.** Методи запускалися на однакових наборах даних (`seed=42`).

| Синтетичних доставок | Тривог (вхідних / об'єднаних) | Доставок із перетином | `scan`, мс | `indexed`, мс | Прискорення, разів |
|---:|---:|---:|---:|---:|---:|
| 1 000 | 371 / 371 | 292 | 12,742 | 0,400 | **31,86×** |
| 10 000 | 371 / 371 | 3 066 | 126,750 | 3,425 | **37,01×** |
| 100 000 | 371 / 371 | 30 579 | 1 205,410 | 31,863 | **37,83×** |

Для кожного обсягу `scan` і `indexed` дають **ідентичні значення по всіх доставках**, що додатково підтверджено рівністю `result_sha256` у CSV. Час запуску залежить від середовища та не є узагальненим показником продуктивності.

Наведені дані — з перерахованого `reports/interval_join_benchmark.csv`; текстовий звіт має відповідати цьому ж запуску. Результати не доводять прискорення PostgreSQL/PostGIS/PySpark, оскільки ці системи поки не тестувалися.

## 7. Ризики і наступні перевірки

| Ризик / прогалина | Вплив | Необхідна дія |
|---|---|---|
| Вихідний пояс часу в `airAlert_2026-10-26.json` не документовано | результати залежать від припущення `Europe/Kyiv` | уточнити в розпорядника; якщо припущення не підтвердиться, повторно нормалізувати первинний JSON і перерахувати експеримент |
| Три події всієї історії з неоднозначним місцевим часом | точні UTC-моменти в переході годинника не визначено; зі статистики інтервалів профілю їх виключено | уточнити джерело або додаткові дані для цих подій перед аналізом відповідного періоду |
| Дві тривоги < 60 с | можливі аномалії даних | переглянути первинні записи, зафіксувати рішення |
| Немає районного просторового покриття | просторовий join не досліджено | отримати й перевірити актуальні полігони районів Києва; окремий етап із PostGIS |
| Всі логістичні події синтетичні, статус випадковий | неможливо довести причинний вплив на логістику | використовувати дані лише для алгоритмічного експерименту, розділяти виміряну експозицію та фактичні затримки |
| Benchmark: лише один запуск, не виміряно пам'ять | оцінка швидкодії нестабільна | зробити 5–10 повторів, фіксувати медіану, оточення та використання пам'яті |
| Не матеріалізовано підсумковий CSV для 500 доставок | недостатньо зручний контроль агрегатів | додати вихідну таблицю експозиції з `delivery_id`, секундами, часткою та кількістю тривог |
| `README.md` порожній | немає наскрізної інструкції на чистому середовищі | документувати команди підготовки й перевірки перед формальним закриттям етапу |

## 8. Критерії приймання і висновок

| Критерій першого етапу | Статус |
|---|---|
| Історичні тривоги та погода | **виконано:** нормалізовані файли існують і перевірені |
| Єдині часові й територіальні ключі | **частково:** `region_id` узгоджений; вихідний час прийнято за `Europe/Kyiv`, але не підтверджено |
| Data Quality: пропуски, дублікати, аномалії | **виконано для трьох CSV**, аномалії коротких тривог задокументовані |
| Мінімум 500 відтворюваних доставок | **виконано:** 500, `seed=42`, поелементна відтворюваність |
| Правильний Interval Join | **виконано для часового PoC:** тестування й два узгоджені методи |
| Базові тести | **виконано:** `10 passed`, плюс перевірки baseline |
| Числовий baseline | **виконано:** 1k / 10k / 100k, один запуск |
| Документація припущень і результатів | **частково:** технічні звіти й контракти підготовлено, README порожній |
| Відтворення на чистому середовищі за README | **не виконано** на поточному етапі |

**Рішення:** продовжувати інженерну роботу над PostgreSQL/PostGIS і просторовою моделлю **можна**, оскільки технічний temporal-join PoC і baseline підтверджені. **Формально вважати перший етап повністю завершеним зарано:** часова зона первинних тривог залишається припущенням, а README та наскрізне відтворення в чистому середовищі ще не підготовлені. README залишається порожнім за попереднім рішенням користувача.

### Відтворення перевірених технічних кроків (за наявності CSV)

Із кореня проєкту, після встановлення залежностей:

```powershell
python scripts/generate_synthetic_deliveries.py
python -m pytest -v
python scripts/interval_join_baseline.py
```

Скрипт baseline читає `data/processed/alerts.csv` та `data/synthetic/deliveries.csv`, а звіт CSV створює у `reports/`. Шлях від сирого JSON до `alerts.csv` проходить через `scripts/prepare_alerts.py` і **потребує верифікації вихідної часової зони**. Команди не заміняють інструкції повної інсталяції на чистому середовищі.
