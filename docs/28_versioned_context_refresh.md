# 28. Версійне оновлення часового контексту

## Що реалізовано

Для дослідної просторової бази додано версії часового контексту. Початкові таблиці й представлення з [документа 27](27_district_context.md) збережено; їхній знімок скопійовано як першу версію. Нове представлення `spatial_research.delivery_district_context_v2` використовує **активну версію**, зберігає всі синтетичні доставки та показує `version_id` і `temporal_snapshot_utc`.

`context_versions` зберігає метадані версій і контрольні суми, `context_version_rows` — їхні рядки, `context_active_version` — посилання на активну версію. Скрипт додає нову версію, не видаляючи й не змінюючи попередні. Це гарантія роботи скрипта, а не захист від ручного редагування власником бази; перевірка виявляє невідповідність даних контрольній сумі.

## Як працює оновлення

`python -m scripts.refresh_versioned_context` перевіряє походження й геометрії районів і точок, поточну активну версію, погодні джерела та сценарії, а тоді зчитує часовий контекст із основної бази. Якщо зміст і контрольні суми не змінилися, команда повертає `unchanged` і не створює дубль.

Якщо перевірені дані змінилися, скрипт створює нову версію та активує її **в одній транзакції просторової бази**. До перемикання перевіряються контрольна сума, усі поля завантажених рядків, повнота й відповідність синтетичним точкам. Попередня версія залишається доступною. Якщо перевірка або транзакція завершується помилкою до `COMMIT`, перемикання і нові рядки відкочуються.

Конкуруючі запуски використовують спільне транзакційне блокування та перевірку очікуваного ID активної версії: запуск, який побачив застарілу версію, завершується помилкою замість її перезапису. На час запису також блокуються та перевіряються просторові вхідні дані. Якщо їх змінили, оновлення припиняється. Це не замінює управління доступом до бази.

Оновлення не змінює самі джерела й не завантажує нові CSV до основної бази. Для нової версії файли, дані та записи про завантаження мають уже узгоджуватися й проходити наявні перевірки. Поточний початковий завантажувач не реалізує загального перезавантаження змінених джерел; це окреме завдання. Процедура працює для наявних 500 синтетичних точок і сценарію `density_uniform_s42_v1`, а не для довільної зміни набору доставок або геометрій.

## Актуальність і межі гарантій

Основна та просторова бази окремі: тут немає розподіленої транзакції між ними. Джерела перевіряються до активації та ще раз після неї. Якщо вони змінилися біля моменту активації, команда повідомить, що збережений знімок потребує повторного оновлення; зафіксована версія залишається в історії. Зміна після останньої перевірки також можлива. Тому команда `python -m scripts.verify_versioned_context` перевіряє активну версію з поточними джерелами й просторовими даними на момент її виконання. Сам SQL-запит у pgAdmin **не блокує** застарілі значення автоматично; перевірку слід виконувати перед використанням результату. Автоматичного розкладу оновлення немає.

Вихідні районні контури залишаються неофіційним спрощеним кандидатом; координати й відключення — синтетичні. Цей крок не вирішує питання актуальності меж і не дає висновків про реальні доставки.

## Перевірка поточного стану

Першу версію звірено по всіх 500 доставках із попереднім знімком, незалежним просторовим еталоном і джерелами. На момент перевірки дані відповідали джерелам: 255 точок із одним збігом, 245 без збігу. Повторна штатна команда оновлення повернула `unchanged`, оскільки джерела не змінились.

Окремий тест використав транзакції, які відкотилися: він змоделював зміну погодного значення, перевірив перемикання активної версії та збереження старої, а також відхилення неповного набору, зміни просторових входів і конфлікту ID активної версії. Логіка команд додатково протестована для незміненого та зміненого джерела. Реального нового завантаження зовнішнього джерела в цій серії не виконували. Звіти перевірок — `reports/versioned_context_validation_20261110.json` та `reports/versioned_context_rechecked_20261110.json`.

## Використання

Одноразове створення версійної структури після кроку 27:

```powershell
python -m scripts.setup_versioned_context
```

Команда відмовляється перезаписувати наявні версійні об'єкти. Для штатного оновлення й перевірки:

```powershell
python -m scripts.refresh_versioned_context
python -m scripts.verify_versioned_context
```

У pgAdmin підключитися до `spatial_research` на порту `55433`. Після успішної перевірки:

```sql
SELECT delivery_id, district_match_status, district_name,
       alert_overlap_seconds, temperature_c, precipitation_previous_hour_mm,
       alert_active, outage_active, version_id, temporal_snapshot_utc
FROM spatial_research.delivery_district_context_v2
ORDER BY delivery_id
LIMIT 20;
```

Історія версій:

```sql
SELECT version_id, created_at, captured_at, scenario_id, row_count, context_sha256
FROM spatial_research.context_versions
ORDER BY created_at;
```

Первинне представлення `spatial_research.delivery_district_context` залишається незміненою історичною копією і **не перемикається** на нові версії. Наступні кроки — механізм контрольованого оновлення джерел, надійніші районні межі та повторне відтворення дослідження з чистого середовища.
