# 19. Вимірювання побудови часових станів

## Постановка і перевірка

Досліджено час виконання `SELECT * FROM scenario.region_state` для трьох сценаріїв із 50, 250 та 1 000 синтетичних відключень і спільними 371 завантаженими тривогами Києва. Кількість отриманих максимальних станів змінюється разом із подіями. Перед серією кожен стан було звірено з незалежним Python-еталоном; окремо перевірено по 500 зіставлень початку доставки для кожного сценарію (`docs/18_delivery_states_by_scenario.md`).

Менші сценарії — вкладені префікси одного згенерованого потоку (`seed=42`), тому це не незалежні реалізації випадкового процесу. Події відключень і доставки модельні й не підтверджують реальних знеструмлень або затримок.

## Методика

На PostgreSQL 17.11 у Docker проведено одне попереднє виконання для кожного сценарію та п'ять вимірів. Порядок у кожному раунді перемішано з фіксованим seed. Запити виконувалися послідовно із `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`; перевірялася кількість отриманих станів. До і після серії звірялися відбитки вихідних записів, визначення сценаріїв і подання. Параметри середовища та плани збережено.

Порівнюється серверний `Execution Time` для динамічного представлення, включно з його поточними перевірками джерела, але без передачі рядків клієнту й підготовки даних. Попередня перевірка та прогрів виконувалися до вимірювань, кеш між запусками не очищувався. Загальне споживання оперативної пам'яті не вимірювалося.

## Результати

| Синтетичних відключень | Станів | Медіана, мс | Мінімум, мс | Максимум, мс |
|---:|---:|---:|---:|---:|
| 50 | 836 | 5,493 | 5,200 | 5,886 |
| 250 | 1 110 | 7,242 | 6,871 | 7,441 |
| 1 000 | 1 430 | 13,628 | 12,785 | 14,490 |

На цих трьох сценаріях медіанний час зростав разом із кількістю подій і результатних станів. Це опис конкретної серії, а не доведення складності алгоритму чи прогноз для великих обсягів. Вплив кількості подій окремо від щільності накладань, числа станів, витрат на валідацію джерела та плану PostgreSQL цим експериментом не ізольовано. У кореневих показниках планів вимірювань тимчасових блоків читання/запису не зафіксовано; це не означає відсутності використання пам'яті.

## Артефакти і повторення

`reports/region_state_benchmark_20261106/` містить `measurements.csv`, `summary.csv`, `metadata.json` і 18 JSON-планів: три прогріви та 15 вимірювань. У metadata збережено повне визначення подання, параметри PostgreSQL, hashes/відбитки джерел і дані сценаріїв. Статус `complete` означає завершену серію та збіг перевіреного стану входів до й після неї.

Для повторення після підготовки бази й сценаріїв:

```powershell
python -m scripts.verify_outage_scenarios
python -m scripts.verify_scenario_delivery_states
python -m scripts.run_region_state_benchmark --output reports/region_state_benchmark_new
```

Папка результату має бути новою. Нові сценарії з іншими seed, щільністю та перетинами, більшими обсягами й додаткові повторення потрібні для ширших висновків. Часові стани тут не матеріалізуються і реальну логістику не вимірюють.
