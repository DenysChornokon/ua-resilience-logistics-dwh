# 03. Контракти даних (Data Contracts)

**Проєкт:** UA-Resilience Logistics DWH  
**Версія:** v0.3, перевірено 28.10.2026  
**Географія PoC:** місто Київ, `region_id = UA80000000000093317`  
**Часове вікно:** `[2026-07-01T00:00:00Z, 2026-10-01T00:00:00Z)`.

## 1. Загальні інваріанти

- Інтервали є напіввідкритими: `[start, end)`. Якщо `end_1 == start_2`, тривалість перетину дорівнює нулю.
- У підготовлених CSV час позначається як UTC (`+00:00`). Для первинного JSON тривог за рішенням користувача прийнято місцевий час `Europe/Kyiv`; після локалізації він переводиться в UTC. Це робоче припущення, не підтверджене розпорядником. До офіційної верифікації кількісні висновки про експозицію є попередніми.
- `region_id` потрібно читати як рядок, а не як число; зв'язування доставок із тривогами допускається лише за однаковими територіальними ключами.
- `data/raw/` зберігає первинні незмінені дані; `data/processed/` — нормалізовані набори; `data/synthetic/` — відтворювані модельні дані. Статуси синтетичних доставок не можна інтерпретувати як виміряну затримку.
- Не відкидати некоректні записи без обліку причин і кількості. Об'єднувати перекриті інтервали тривог перед підрахунком сумарної експозиції, інакше можливе подвійне зарахування секунд.
- Пропущені значення, повторні ключі, порушення меж періоду та неузгоджені часові пояси є порушеннями контракту або зафіксованими обмеженнями джерела.

## 2. Історія тривог: `data/processed/alerts.csv`

**Джерело:** `data/raw/alerts/airAlert_2026-10-26.json`. **Скрипт:** `scripts/prepare_alerts.py`.  
**Гранулярність:** один рядок на окрему завершену подію тривоги Києва, що перетинає досліджуваний період; інтервал обрізається до меж вікна.

| Поле | Тип | Правила |
|---|---|---|
| `event_id` | string | непорожній, унікальний; походить із `uid` |
| `region_id` | string | `UA80000000000093317`, походить із `CATUTTC` |
| `region_name` | string | `місто Київ`, походить із `addressAdminUnitL2` |
| `event_type` | string | `Повітряна тривога`, походить із `type` |
| `started_at` | timezone-aware timestamp | походить із `dateTimeStart`; раніше за `finished_at` |
| `finished_at` | timezone-aware timestamp | походить із `dateTimeEnd`; пізніше за `started_at` |

**Застосована трансформація:** `dateTimeStart` / `dateTimeEnd` без зони трактуються як `Europe/Kyiv` і переводяться в UTC; неоднозначні та неіснуючі через перехід годинника мітки серед кандидатів викликають помилку. Для вибірки Києва спочатку визначаються кандидати із запасом часу, далі після локалізації та перетворення відбираються події зі строгим перетином із UTC-вікном `[2026-07-01, 2026-10-01)`. Часи обмежуються межами цього вікна. Інтервали з незрозумілими датами не відкидаються непомітно.

**Контроль якості:** перерахований `alerts.csv` містить **371 рядок, 6 колонок, 0 пропусків, 0 повних дублікатів, 0 повторних `event_id`, 0 інтервалів із `finished_at <= started_at`**. Також виявлено **2 події тривалістю менше 60 секунд** для подальшої ручної перевірки. Інтервали цієї вибірки не перетинаються; алгоритм об'єднання інтервалів усе одно залишається обов'язковим для загального випадку.

**Невирішено:** офіційна часова зона вихідних дат без зміщення. Позначка `+00:00` у вихідному CSV виникає після нормалізації й нічого не доводить про початковий часовий пояс.

**Профіль усієї історії:** із 2 736 записів три події (`1837`, `2729`, `2730`) мають неоднозначні локальні мітки під час переведення годинника. Вони збережені у первинному JSON і окремо зазначені в `reports/air_alerts_profile.json`, але виключені зі статистики інтервалів профілю; вона обчислена для 2 733 однозначних інтервалів. Ці події не входять до обраного літньо-осіннього UTC-вікна PoC.

## 3. Погода: `data/processed/kyiv_weather.csv`

**Джерело:** Open-Meteo Historical Weather API; координати `50.4501, 30.5234`; параметри `temperature_2m`, `precipitation`, `wind_speed_10m`, `timezone=GMT`.  
**Гранулярність:** один погодинний запис на одну точку. Для початкового join модельне погодинне вікно задається як `[time, time + 1 година)`; часову семантику конкретної змінної потрібно враховувати при фізичній інтерпретації.

| Поле | Тип | Правила |
|---|---|---|
| `time` | timezone-aware timestamp | UTC, унікальний; строго 1-годинний крок |
| `temperature_2m` | float | °C; перевірка фізичної правдоподібності |
| `precipitation` | float | мм; не менше нуля |
| `wind_speed_10m` | float | км/год; не менше нуля |

**Контроль якості:** наданий CSV містить **2 208 рядків, 4 колонки, 0 пропусків, 0 повних дублікатів і 0 повторних часових міток**. Усі **2 207** послідовних кроків становлять 1 годину. Охоплення: `2026-07-01 00:00 UTC` — `2026-09-30 23:00 UTC`. Температура: **7,5–37,6 °C**; опади за період: **177,7 мм**; швидкість вітру: **0–24,9 км/год**.

## 4. Синтетичні доставки: `data/synthetic/deliveries.csv`

**Джерело:** `scripts/generate_synthetic_deliveries.py`; `numpy.random.default_rng(seed=42)`; результат відтворено з наданого скрипта.  
**Гранулярність:** один рядок на синтетичну доставку в межах міста Києва.

| Поле | Тип | Правила |
|---|---|---|
| `delivery_id` | string | унікальний, формат `D-00001` тощо |
| `region_id` | string | `UA80000000000093317`; збігається з `alerts.region_id` |
| `started_at` | timezone-aware timestamp | від `2026-07-01T00:00:00Z` включно |
| `finished_at` | timezone-aware timestamp | пізніше за `started_at`, не після `2026-10-01T00:00:00Z` |
| `distance_km` | float | модельна відстань 0,5–20,0 км |
| `status` | string/category | `completed`, `delayed`, `cancelled`; призначено випадково, незалежно від тривог |

**Контроль якості:** надано **500 рядків, 6 колонок**, **0 пропусків, 0 повних дублікатів, 0 повторних `delivery_id`, 0 невалідних інтервалів**. Усі регіональні ключі збігаються з ключем Києва в тривогах. Статуси: `completed` — **416**, `delayed` — **55**, `cancelled` — **29**. Усі перевірені значення відповідають повторній генерації з `seed=42` і наданим кодом (порівняно по полях).

## 5. Контракт Interval Join

**Вхід:** одна доставка `D = [d_start, d_end)` і список тривог `A_i = [a_start, a_end)` для тієї самої території.  
**Умова перетину:** `d_start < a_end AND a_start < d_end`.  
**Тривалість перетину пари:** `max(0, min(d_end, a_end) − max(d_start, a_start))` секунд.

Перш ніж сумувати експозицію доставки, інтервали тривог для регіону треба впорядкувати та злити, якщо вони перекриваються або торкаються. Загальна експозиція `0 <= alert_overlap_seconds <= delivery_duration_seconds`.

**Цільова схема результату (поки не матеріалізована окремим CSV):**

| Поле | Тип | Умова |
|---|---|---|
| `delivery_id` | string | один рядок на доставку, включно з нульовими перетинами |
| `alert_overlap_seconds` | numeric | секунди перетину з об'єднанням тривог, >= 0 |
| `alert_exposure_ratio` | float | `alert_overlap_seconds / delivery_duration_seconds`, в межах [0, 1] |
| `overlap_alert_count` | integer | число вихідних подій, що перетинають доставку |

**Наявна реалізація:** `src/poc_interval_join.py` містить чисту функцію `overlap_seconds` для **однієї пари інтервалів**; `scripts/interval_join_baseline.py` містить `merge`, `scan` та `indexed` для **агрегованої експозиції доставки**. Скрипт benchmark створює `reports/interval_join_benchmark.csv` та `reports/interval_join_metadata.json`, але не матеріалізує окремий CSV з усіма 500 доставками й полями цільової схеми. Описувати цільову схему як уже реалізований артефакт не слід.
