# 23. Порівняння зіставлення доставок зі станами

## Постановка

Порівняно початкове динамічне представлення `scenario.delivery_start_state` з експериментальним варіантом для тих самих дев'яти сценаріїв із [документа 22](22_delivery_density_benchmark.md). В обох випадках використовуються однакові 500 синтетичних доставок, 250 синтетичних відключень на сценарій і завантажені записи реальних повітряних тривог. Стан визначається на початку доставки; погода й фактичні затримки не досліджуються.

Початковий запит щоразу будує стани регіону та зіставляє з ними доставки. Експериментальний варіант спочатку будує стани одного сценарію в тимчасовій таблиці поточної сесії, створює GiST-індекс часових інтервалів і запускає `ANALYZE`. Далі запит зіставляє доставку з напіввідкритим інтервалом `[початок, кінець)` через індекс. Таблиця не є постійним сховищем і автоматично зникає після завершення сесії. За кожної зміни джерел, визначення стану чи сценарію її треба будувати заново; автоматичного оновлення немає. Це дослідний варіант, а не впроваджена заміна робочого представлення.

## Перевірка правильності

До і після серії незалежний Python-еталон перевірив усі 4 500 результатів початкового представлення, джерела і сценарії, як у документі 22. У кожному з 54 парних запусків обидва SQL-результати порівнювалися по всіх полях із `EXCEPT ALL` в обидва боки; розбіжностей і втрат рядків не виявлено. Окрема тестова транзакція перевірила обидва способи на початкових і кінцевих межах, іншому регіоні та за невідомого стану; її зміни відкотилися.

## Умови вимірювань

PostgreSQL 17.11; дев'ять сценаріїв, один прогрів і п'ять вимірювальних повторів для кожного. Порядок сценаріїв та порядок методів у парі псевдовипадкові. Для кожної пари тимчасову таблицю й індекс створювали заново в окремій сесії. Підготовку виконували до обох вимірювань; перевірка результатів також виконувалась до них, тому дані могли бути прогрітими. Кеш не очищався.

Час запитів — `Execution Time` із `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`. Підготовку виміряно за серверним годинником окремо для створення таблиці, індексу та `ANALYZE`; вона включає невеликі накладні витрати вимірювальних SQL-команд. Для кожної пари обчислено суму підготовки та часу індексованого запиту. Це **оцінка суми виміряних компонентів**, а не повний час роботи програми: вона не включає перевірку результатів, час планування, створення з'єднання, передачу всіх рядків клієнтові та завершення сесії. Так само час початкового запиту не включає ці складові. Загальне споживання пам'яті не вимірювалося.

## Результати

Таблиця показує медіану трьох медіан окремих seed; кожна медіана seed отримана з п'яти повторів. Сума підготовки та індексованого запиту спочатку обчислювалась окремо для кожного парного запуску, а потім бралась медіана.

| Профіль | Початковий запит, мс | Підготовка, мс | Запит з індексом, мс | Підготовка + запит, мс |
|---|---:|---:|---:|---:|
| sparse | 51,200 | 20,898 | 4,920 | 25,372 |
| uniform | 48,265 | 19,803 | 4,995 | 24,632 |
| clustered | 35,215 | 20,561 | 4,825 | 25,035 |

У цій серії оцінена сума підготовки та запиту була меншою за початковий запит у всіх дев'яти сценаріях за медіанами окремих seed. Медіанна оцінка точки окупності — один запит у кожному сценарії: `ceil(підготовка / (початковий запит − індексований запит))`. Це наближення для конкретних вимірюваних компонентів, не гарантія повного часу одного реального запиту. Наприклад, у `clustered`, seed 43, окремі оцінки суми становили 22,496–36,214 мс, а початковий запит — 33,134–36,564 мс: діапазони перекриваються. Повторне використання знімка може амортизувати підготовку, але допустиме лише поки вхідні дані й логіка станів не змінилися.

У всіх 54 індексованих планах використано `delivery_state_cache_range_idx`. Порівняння одночасно змінює матеріалізацію, індексацію та форму умови зіставлення, тому не визначає окремий внесок кожної з них. Значення не можна переносити на інші розміри, комп'ютери чи холодний кеш без окремого досліду. П'ять повторів вимірюють мінливість виконання одних і тих самих сценаріїв; вони не є незалежними наборами даних. У базі під час серії було 13 визначень сценаріїв і 3 554 події відключення загалом, що може впливати на побудову станів. До і після серії збережено контрольні суми вхідних таблиць та визначення обох представлень; це перевірка знімків, а не безперервний моніторинг.

## Відтворення

За наявності бази, Docker, завантажених джерел і дев'яти сценаріїв:

```powershell
python -m scripts.verify_delivery_cache_boundaries
python -m scripts.run_delivery_cache_benchmark --output reports/delivery_cache_new_run
```

Перша команда виконує тестові операції в транзакції з відкатом. Друга сама перевіряє дані до і після серії та порівнює обидва результати перед кожним вимірюванням. Потрібен новий каталог: наявний не перезаписується. Сирі вимірювання, зведення для кожного seed, метадані і 108 планів збережено в `reports/delivery_cache_benchmark_20261107/`.

У pgAdmin можна випробувати один сценарій у **новій вкладці Query Tool**, виконавши всі команди разом в одному підключенні:

```sql
CREATE TEMP TABLE delivery_state_cache AS
SELECT * FROM scenario.region_state
WHERE scenario_id = 'density_sparse_s41_v1';

CREATE INDEX delivery_state_cache_range_idx ON delivery_state_cache
USING gist (tstzrange(started_at, finished_at, '[)'));
ANALYZE delivery_state_cache;

SELECT s.scenario_id, d.delivery_id, d.region_id,
       d.started_at AS delivery_started_at,
       r.started_at AS state_started_at, r.finished_at AS state_finished_at,
       (r.started_at IS NOT NULL) AS state_known, r.alert_active, r.outage_active
FROM scenario.definitions s
JOIN core.fact_delivery d ON d.region_id = s.region_id
 AND d.started_at >= s.window_start AND d.started_at < s.window_end
LEFT JOIN pg_temp.delivery_state_cache r ON r.scenario_id = s.scenario_id
 AND r.region_id = d.region_id
 AND tstzrange(r.started_at, r.finished_at, '[)') @> d.started_at
WHERE s.scenario_id = 'density_sparse_s41_v1';
```

Таблиця діє лише в цьому підключенні. Для нового запуску підготовки відкрийте нове підключення або закрийте попередню сесію; інакше назва таблиці вже існуватиме. Запит показує модельний стан, а не повну експозицію протягом доставки.

Перевірку перебудови станів після зміни тестових даних та результати для більших наборів наведено в [документі 24](24_cache_refresh_and_scaling.md).
