# 25. Погодні умови та контекст доставки

## Що реалізовано

`mart.delivery_start_weather` додає до кожної доставки погодний запис для початку доставки. Для київського `region_id = UA80000000000093317` застосовується лише заздалегідь визначена точка `kyiv_open_meteo` з координатами запиту `50.4501, 30.5234`. Це наближення однією точкою, а не просторове зіставлення адрес чи районів. Для інших регіонів погодні поля залишаються невідомими.

Для доставки в інтервалі `[T, T + 1 година)` береться запис рівно на годину `T` у UTC. Це остання доступна погодна мітка на початок доставки, без використання наступної години. Присвоєння значення всій наступній годині — модельне правило, не твердження, що погода залишалася сталою. На точній межі години використовується нова мітка. Якщо запису саме для цієї години немає, він не замінюється старішим: `weather_known = false`, погодні значення — `NULL`, доставка зберігається.

Згідно з [документацією Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api), температура й швидкість вітру є значеннями на вказаний момент `T`, а `precipitation` — сумою за годину **перед** `T`. Тому поле вітрини названо `precipitation_previous_hour_mm`. Наприклад, для доставки о 10:40 UTC використовується запис на 10:00, а опади відносяться до години перед 10:00; це не кількість опадів за час доставки і не опади саме о 10:40. Значення 0 означає нульові опади у цьому погодному записі; `NULL` означає невідоме значення. Наявний історичний продукт Open-Meteo є погодними даними моделі/реаналізу для точки, а не перевіреним фактичним виміром уздовж маршруту.

Погодні значення надаються лише за наявності успішного завантаження погоди, якщо кількість записів та `load_id` відповідають цьому завантаженню. Перевірка консервативно передбачає одне погодне завантаження для всієї поточної таблиці; для багатьох джерел і оновлень потрібна окрема модель версій. Вона не доводить повноти або достовірності початкового джерела.

`mart.delivery_context` об'єднує доставку, наявні показники експозиції до тривог та цю погодну ознаку. Параметр `alert_data_available` лише показує, чи повернула рядок поточна вітрина тривог; він не підтверджує повного покриття джерела. Якщо вітрина тривог недоступна, її показники залишаються `NULL`. Доставки й відключення в дослідженні синтетичні, а стан тривоги/відключення у сценарії та погодне значення — на початок доставки. `alert_overlap_seconds` натомість стосується всієї тривалості доставки; ці показники не доводять затримки чи причинного впливу.

## Перевірка поточного зрізу

`scripts.verify_delivery_weather` звірив усі 2 208 погодних записів у базі з CSV, часи й регіони всіх 500 доставок — з їхнім CSV, а також контрольні суми цих файлів із записами завантаження. Усі 500 рядків обох вітрин зіставлено з незалежним Python-правилом: **500 відомих погодних значень, 0 невідомих, розбіжностей немає**. У 60 із 500 випадків обраний погодний запис містить додатні опади за годину перед його міткою; це не означає, що ці 60 доставок відбувалися під дощем.

Показники тривог для всіх 500 доставок окремо перевірено `scripts.verify_alert_exposure`: 154 доставки мають ненульову експозицію, загалом 293 671 секунду; результати збіглися. Тестова SQL-транзакція перевірила початок і кінець години, інший часовий пояс сесії, нуль опадів, пропущену годину, інший регіон та недоступні погодне і тривожне завантаження. Тестові зміни відкотилися.

Контрольні суми, кількості та визначення вітрин зафіксовано в `reports/delivery_weather_validation_20261107.json`. Перевірка описує поточні джерела й не є оцінкою точності реальних погодних умов, затримок або повноти всієї історії.

## Відтворення та pgAdmin

Після створення схеми, завантаження трьох CSV і створення `mart.delivery_alert_exposure` застосувати нові представлення один раз:

```powershell
docker compose exec -T db psql -X -v ON_ERROR_STOP=1 -U dwh_user -d logistics_dwh -f /sql/09_delivery_weather_context.sql
python -m scripts.verify_delivery_weather
python -m scripts.verify_alert_exposure
```

SQL-файл створює нові представлення і не перезаписує наявні; якщо назви вже зайняті, транзакція завершується помилкою. Для повторної перевірки без нового звіту достатньо двох команд Python. Новий JSON можна зберегти через `python -m scripts.verify_delivery_weather --output reports/delivery_weather_new_run.json`: наявний файл не перезаписується.

У pgAdmin, у Query Tool бази `logistics_dwh`:

```sql
SELECT delivery_id, delivery_started_at, alert_overlap_seconds,
       weather_observed_at, temperature_c, wind_speed_kmh,
       precipitation_previous_hour_mm, weather_known
FROM mart.delivery_context
ORDER BY delivery_started_at
LIMIT 20;
```

Щоб доповнити це одним із синтетичних сценаріїв відключень:

```sql
SELECT c.delivery_id, c.delivery_started_at, c.alert_overlap_seconds,
       c.temperature_c, c.precipitation_previous_hour_mm,
       s.alert_active, s.outage_active
FROM mart.delivery_context c
JOIN scenario.delivery_start_state s
  ON s.delivery_id = c.delivery_id AND s.region_id = c.region_id
WHERE s.scenario_id = 'density_sparse_s42_v1'
ORDER BY c.delivery_started_at
LIMIT 20;
```

Перший запит не потребує сценарію відключень. Другий потребує вже створеного `scenario.delivery_start_state` і завантаженого обраного сценарію. Ці запити показують модельний аналітичний контекст, а не фактичні причини затримок.
