# 15. Прототип багатофакторних станів регіону

Цей крок додає контрольований сценарій для Києва: історичні тривоги з `core.fact_alert` і **чотири вручну задані синтетичні відключення**. Відключення створені для перевірки алгоритму та не є повідомленнями про реальні знеструмлення. Погода на цьому кроці не включена; вона не вважається відсутньою чи сприятливою.

## Модель

`scenario.definitions` описує ідентифікатор сценарію, територію і напіввідкрите UTC-вікно. `scenario.outage_events` зберігає модельні події з `source_type='synthetic'`. Кожна подія має власні часові межі; ідентифікатори не зливаються з початковими записами тривог.

`scenario.region_state` — динамічне представлення. Один рядок описує максимальний неперекривний відрізок `[started_at, finished_at)` у межах конкретного сценарію, з окремими ознаками `alert_active`, `outage_active` і `duration_seconds`. Нульові стани включені для повного покриття вікна. `alert_active=false` означає відсутність події у завантаженій вибірці; це не самостійне підтвердження повноти першоджерела. `outage_active=false` означає відсутність синтетичного відключення в сценарії, а не підтверджену наявність електрики.

SQL обрізає події межами сценарію, групує одночасні початки й закінчення, накопичує кількість активних подій кожного фактора та зливає суміжні сегменти з однаковими ознаками. Вкладені, перекриті й дотичні інтервали одного типу не створюють хибного відбою, поки діє інша подія того самого типу. За відсутності узгодженого успішного завантаження тривог представлення не повертає стани.

## Створення і перевірка

Після створення `core` та завантаження початкових даних:

```powershell
docker compose exec -T db psql -U dwh_user -d logistics_dwh -v ON_ERROR_STOP=1 -f /sql/07_multifactor_states.sql
python -m scripts.verify_multifactor_states
```

SQL створює нові таблиці та представлення один раз і не перезаписує наявні об'єкти. Python-скрипт незалежно ділить вікно за всіма межами та поелементно порівнює кожен отриманий стан із SQL. `tests/test_multifactor_states.sql` перевіряє контрольні дані в транзакції з `ROLLBACK`; `tests/test_multifactor_reference.py` перевіряє еталон.

У pgAdmin, в Query Tool бази `logistics_dwh`:

```sql
SELECT * FROM scenario.region_state
WHERE scenario_id='kyiv_demo_v1'
ORDER BY started_at;
```

```sql
SELECT alert_active, outage_active, count(*) AS states,
       sum(duration_seconds) AS seconds
FROM scenario.region_state
WHERE scenario_id='kyiv_demo_v1'
GROUP BY alert_active, outage_active
ORDER BY alert_active, outage_active;
```

Результат залежить від поточного вмісту `core.fact_alert`: це представлення, а не версійований матеріалізований знімок. Його не можна використовувати для оцінки фактичних відключень або причинного впливу на доставки. Подальші кроки — простежувані версії сценаріїв і станів, point-in-interval зіставлення, тестування погодного фактора та окремий експеримент продуктивності.
