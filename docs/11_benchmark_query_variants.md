# 11. Варіанти запиту для benchmark

`sql/05_benchmark_query_variants.sql` створює окремий знімок тривог `benchmark.alert_events`, метадані його походження `benchmark.alert_snapshot`, GiST-індекс на часовому діапазоні тривог і шість представлень `benchmark.baseline_10000`, `benchmark.range_10000` тощо. Існуючі таблиці не перезаписуються. Створення виконується транзакційно й відмовляє за відсутнього або неузгодженого завантаження тривог.

Кожна пара використовує один знімок тривог і одну таблицю доставок, однаковий алгоритм злиття часових перетинів, підрахунок вихідних подій та ідентичні поля результату. Варіант `baseline` шукає кандидатів через нерівності часових меж; `range` — через оператор перетину `tstzrange`. Для останнього створено GiST-індекс, але оптимізатор сам обирає план. Жодне прискорення наперед не гарантується.

```powershell
docker compose exec -T db psql -U dwh_user -d logistics_dwh -v ON_ERROR_STOP=1 -f /sql/05_benchmark_query_variants.sql
python -m scripts.verify_benchmark_variants
```

Перевірка зіставляє всі рядки кожного з шести представлень з незалежним Python-розрахунком за локальними CSV. SQL-випадки `tests/test_benchmark_variants.sql` перевіряють вкладення, накладання, дотичні межі, інший регіон та нульову експозицію; їх потрібно запускати через psql із `ON_ERROR_STOP=1`, після чого транзакція виконує `ROLLBACK`.

Запити використовують синтетичні доставки і знімок тривог. Якщо вихідні тривоги або benchmark-таблиці зміняться, потрібно створити новий погоджений знімок та повторити перевірку; цей скрипт нічого не перезаписує. Знімок, індекс і перевірка коректності — підготовка: показники швидкодії тут не вимірюються. Для порівняння слід окремо зафіксувати плани `EXPLAIN (ANALYZE, BUFFERS)`, час і розподіл повторів, включно з витратами на підготовку індексу.
