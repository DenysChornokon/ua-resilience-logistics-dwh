# 35. Запуск і демонстрація проєкту в pgAdmin

## Що показує демонстрація

Ми переглянемо підготовлені дані, перетини доставок із тривогами, погодний контекст, синтетичний сценарій відключень і дослідне зіставлення з районами. Наприкінці можна показати графік результатів вимірювання швидкодії.

Тривоги походять із підготовленого історичного джерела; погода — модельні погодинні дані для однієї точки. **Доставки, їхні координати та відключення синтетичні**, а районні контури — неофіційні. Тому демонстрація показує можливості прототипу, а не фактичні затримки чи підтверджені межі районів.

Сценарій нижче розрахований на **вже створені та заповнені бази цього проєкту**. Усі наведені демонстраційні запити лише читають дані. Якщо бази ще не розгорнуто, перед демонстрацією потрібна окрема підготовка за документами 06 та 26–28; сам запуск контейнерів не створює потрібних вітрин і даних.

## 1. Запустити бази та перевірити результати

1. Відкрийте Docker Desktop і дочекайтеся запуску Docker Engine.
2. Відкрийте PowerShell у папці проєкту. Якщо обидва контейнери вже працюють, повторно запускати їх не потрібно. Для **вже створених** контейнерів, які зупинені, виконайте:

   ```powershell
   docker compose -f compose.yaml -f compose.spatial.yaml --profile spatial-research start db spatial-db
   ```

3. Із тієї самої папки запустіть перевірку:

   ```powershell
   .\.venv\Scripts\python.exe -m scripts.verify_demo
   ```

Успішний результат містить `"status": "verified"`. Команда незалежно перевіряє експозицію й погоду, виконує вісім запитів у транзакціях лише для читання та перевіряє актуальність просторової версії до і після них. Це перевірка на два моменти часу: якщо джерела зміняться пізніше, запустіть команду знову. Автоматичного безперервного контролю між двома базами немає.

Якщо перевірка повідомляє про відсутні таблиці, файли чи неактуальну версію, усуньте причину перед показом. Перевірка не створює відсутні об'єкти й не перезаписує дані. За потреби результат можна зберегти в **новий** файл: додайте `--output reports/demo_check_new.json`. Без цього параметра команда лише виводить результат у термінал.

## 2. Підключити дві бази в pgAdmin

Відкрийте pgAdmin на тому самому комп'ютері. Якщо підключення вже створені, використайте їх. Інакше для кожної бази окремо натисніть правою кнопкою **Servers → Register → Server…**. На вкладці **General** задайте довільну зрозумілу назву; на вкладці **Connection** введіть:

| Поле | Основна база | Просторова база |
|---|---|---|
| Назва підключення, приклад | `DWH — логістика` | `DWH — райони` |
| Host name/address | `127.0.0.1` | `127.0.0.1` |
| Port | `55432` | `55433` |
| Maintenance database | `logistics_dwh` | `spatial_research` |
| Username | `dwh_user` | `dwh_user` |
| Password | значення `POSTGRES_PASSWORD` із локального `.env` | те саме значення з `.env` |

Натисніть **Save**. Пароль береться з локального файлу проєкту; його не потрібно вставляти в SQL або надсилати комусь. Ці адреси стосуються pgAdmin, запущеного на тому самому комп'ютері, що й Docker.

## 3. Показати основну базу

1. У дереві pgAdmin відкрийте підключення до `logistics_dwh`, розгорніть **Databases** та виберіть базу `logistics_dwh`.
2. Відкрийте **Tools → Query Tool**. Через кнопку відкриття файлу в редакторі завантажте `sql/demo_logistics.sql` із папки проєкту.
3. Запити в файлі позначено мітками `DEMO`. Виділіть мишею **один запит від `SELECT` до крапки з комою включно** та натисніть кнопку виконання. Так окремо покажіть кожний результат у нижній таблиці.

| Запит | Що показати | Контрольний результат для перевіреного зрізу |
|---|---|---|
| `source_counts` | Скільки записів є в трьох наборах. | 371 тривога, 500 синтетичних доставок, 2 208 погодних записів. |
| `overview` | Скільки доставок хоча б частково перетнули тривогу; загальна експозиція; наявність погоди. | 154 доставки; 293 671 секунда сумарного перетину; погода відома для 500. |
| `delivery_examples` | Десять доставок із найбільшим перетином, погоду та стан обраного сценарію. | По одному рядку на доставку; часи в колонках із суфіксом `_kyiv` — місцевий час Києва. |
| `scenario_counts` | Кількість доставок за станом тривоги та модельного відключення на **початку**. | Для `density_uniform_s42_v1`: 341 без обох факторів, 64 лише з відключенням, 83 лише з тривогою, 12 з обома. |

У `overview` поле `unknown_alert_exposure` відрізняє невідомі дані від нульового перетину. У прикладах `state_known` і `scenario_row_present` показують, чи відомий сценарний стан; `NULL` не означає відсутність події. Значення `precipitation_previous_hour_mm` — опади за годину **перед погодною міткою**, а не кількість опадів під час усієї доставки.

Числа 154 та 95 не суперечать одне одному: 154 — доставки з перетином тривоги **в будь-який момент доставки**, тоді як 95 = 83 + 12 — доставки, що почалися під час тривоги в показаному сценарії.

## 4. Показати просторову базу

1. У дереві pgAdmin виберіть інше підключення та базу `spatial_research`.
2. Відкрийте новий **Query Tool**, завантажте `sql/demo_spatial.sql` і виконуйте кожен запит окремо. Для запиту, який починається з `WITH`, виділяйте його **від `WITH` до крапки з комою**.

| Запит | Що показати | Контрольний результат для перевіреного зрізу |
|---|---|---|
| `active_version` | Активну версію, сценарій, кількість рядків і момент знімка. | Одна активна версія, 500 рядків, `density_uniform_s42_v1`. |
| `match_counts` | Скільки синтетичних точок зіставлено з одним, жодним або кількома контурами. | `matched` — 255, `unmatched` — 245, `ambiguous` — 0. |
| `district_examples` | Приклади точок із єдиним знайденим районом і часовим контекстом. | До 10 рядків із кодом активної версії та назвою району. |
| `district_summary` | Модельні підсумки лише для точок із єдиним районом. | Загалом 255 точок у десяти рядках районів для цього зрізу. |

Поле `captured_at_utc` показує час створення знімка в UTC, але **саме по собі не доводить його актуальності**. Для цього потрібна перевірка з кроку 1. `matched` означає один збіг із дослідним контуром, `unmatched` — жодного, `ambiguous` — декілька; у двох останніх випадках район не обирається довільно. Число 245 не є кількістю реальних доставок поза містом: точки синтетичні й створені за іншим історичним контуром.

## 5. Показати підсумок дослідження

Відкрийте [підсумковий документ](34_research_synthesis.md) або [графік чотирьох серій](../reports/research_synthesis_20261111/research_comparison.png). Порівнюйте варіанти **всередині кожної серії**: різні серії виконують різну роботу. Під час пояснення зазначте синтетичні дані, неофіційні контури, кількість повторів та те, що час передавання результату клієнту не вимірювався.

Запити й перевірка виконані 11.11.2026 на наявних базах; машинний результат — `reports/pgadmin_demo_validation_20261111.json`. Окремо перевірено доступність локальних портів і авторизацію паролем через TCP усередині кожного контейнера. Інтерфейс pgAdmin автоматично не перевірявся. Значення вище є контрольними для цього зрізу і можуть змінитися після погодженого оновлення даних.
